# Nexus 5 InternalBlue 설정 및 KNOB 테스트 — 2026-03-18

## 디바이스 정보

- **모델**: LG Nexus 5 (hammerhead), D821(H) 16GB (해외판)
- **HW revision**: rev_11
- **Bootloader**: HHZ20h
- **Baseband**: M8974A-2.0.50.2.30
- **Serial**: 04b7d0512524a642
- **Bluetooth chip**: Broadcom BCM4335C0 (chip ID: 0x6109, firmware 003.001.009)
- **Host machine**: Lenovo V15 G4 IRU, Ubuntu 22.04

## 완료된 설정 단계

### 1. Bootloader Unlock

디바이스를 fastboot 모드(볼륨 다운 + 전원)로 진입시켰습니다. `fastboot oem unlock` 명령으로 bootloader를 unlock하였으며, 이 과정에서 모든 데이터가 초기화되었습니다. 참고: fastboot 모드에서는 `adb`가 동작하지 않으므로, `fastboot devices` 명령으로 연결을 확인해야 합니다.

### 2. Android 6.0.1 Factory Image Flash

Google 공식 factory image `hammerhead-m4b30z`를 `flash-all.sh`로 flash하였습니다. Ubuntu의 fastboot 도구에 포함된 `mke2fs`가 오래된 버전이어서 `userdata` 파티션 포맷이 실패하였습니다. `fastboot erase userdata`와 `fastboot erase cache`를 실행한 후, Android 최초 부팅 시 자동 포맷되도록 하여 해결하였습니다.

### 3. CF-Auto-Root를 이용한 루팅

Chainfire의 hammerhead용 CF-Auto-Root를 사용하였습니다. 다운로드 URL이 브라우저를 통해서만 접근 가능하였습니다(wget으로는 HTML redirect 페이지만 받아집니다). ZIP 파일을 다운로드한 후 아래 명령으로 flash하였습니다:

```bash
sudo fastboot boot image/CF-Auto-Root-hammerhead-hammerhead-nexus5.img
```

SuperSU가 자동으로 설치되었습니다. `adb shell su -c "whoami"`가 `root`를 반환하는 것으로 확인하였습니다.

### 4. Debug Bluetooth Stack 설치

InternalBlue 저장소의 (`android/android6_0_1/`)에서 미리 빌드된 `bluetooth.default.so`를 디바이스에 push하였습니다:

```bash
adb push bluetooth.default.so /sdcard/bluetooth.default.so
adb shell 'su -c "mount -o remount,rw /system"'
adb shell 'su -c "cp /sdcard/bluetooth.default.so /system/lib/hw/bluetooth.default.so"'
adb shell 'su -c "chmod 644 /system/lib/hw/bluetooth.default.so"'
adb shell 'su -c "chown root:root /system/lib/hw/bluetooth.default.so"'
```

이 prebuilt 라이브러리는 HCI forwarding과 H4 Broadcom Diagnostics가 활성화되어 있으며, AOSP 태그 `android-6.0.1_r81`과 일치합니다. 소스에서 직접 빌드하려면 100GB의 AOSP 트리가 필요하므로, 별도로 빌드하지 않았습니다.

Developer Options에서 **Bluetooth HCI snoop log**를 활성화하였습니다.

### 5. BluetoothAssistant APK 빌드 및 설치

BlueToolkit의 `install.sh`에는 알려진 버그(#17)가 있어, BluetoothAssistant 설치 경로가 올바르게 동작하지 않습니다. Gradle을 사용하여 APK를 수동으로 빌드하였습니다:

- Google에서 Android SDK command-line tools를 설치하였습니다(apt로 설치되는 `sdkmanager`는 VanillaIceCream preview SDK를 설치하므로 정상 동작하지 않습니다).
- `~/android-sdk` 경로에 `platforms;android-34`와 `build-tools;34.0.0`으로 SDK를 설정하였습니다.
- Android 6.0.1(API 23)을 지원하기 위해 `app/build.gradle`과 `utilities/build.gradle` 양쪽에서 `minSdk`를 24에서 23으로 낮추었습니다.
- `./gradlew assembleDebug`로 빌드한 후 `adb install`로 설치하였습니다.

필요한 권한은 수동으로 부여하였습니다:

```bash
adb shell pm grant xie.morrowind.tool.btassist android.permission.ACCESS_COARSE_LOCATION
adb shell pm grant xie.morrowind.tool.btassist android.permission.ACCESS_FINE_LOCATION
adb shell pm grant xie.morrowind.tool.btassist android.permission.WRITE_EXTERNAL_STORAGE
adb shell pm grant xie.morrowind.tool.btassist android.permission.READ_EXTERNAL_STORAGE
adb shell mkdir -p /storage/emulated/0/Documents
```

### 6. InternalBlue cmd2 수정

InternalBlue CLI에서 `ImportError: cannot import name 'Fg' from 'cmd2'` 오류가 발생하였습니다. BlueToolkit venv에 cmd2 3.4.0이 설치되어 있었으나, InternalBlue는 2.4.x 버전이 필요합니다. venv에 직접 설치하여 해결하였습니다:

```bash
/usr/share/BlueToolkit/.venv/bin/python -m pip install cmd2==2.4.2
```

### 7. BlueToolkit Exploit Shell Script 수정

`/usr/share/BlueToolkit/modules/tools/custom_exploits/` 하위의 InternalBlue exploit shell script들에서 여러 문제가 발견되었습니다:

- **Shebang 누락**: 스크립트에 `#!/bin/bash` 줄이 없었습니다. 모든 `internalblue_*.sh` 파일에 `sed -i '1i#!/bin/bash'`로 추가하여 수정하였습니다.
- **잘못된 Python 경로**: 스크립트에서 `python3`을 사용하고 있었으나, InternalBlue는 BlueToolkit venv에 설치되어 있습니다. 아래 명령으로 수정하였습니다:
  ```bash
  sed -i 's|python3 \.\./internalblue|/usr/share/BlueToolkit/.venv/bin/python ../internalblue|g' internalblue_*.sh
  ```
- **KNOB PoC 블로킹**: `KNOB_PoC.py` 스크립트가 interactive CLI(`cmdloop()`)를 열어 shell script를 블로킹합니다. non-interactive 커스텀 스크립트(`bluekit_internalblue_knob.py`)로 대체하였습니다.

## KNOB Attack 테스트

### InternalBlue KNOB의 동작 원리

KNOB attack(CVE-2019-9506)은 Bluetooth encryption key negotiation을 악용합니다. InternalBlue는 Nexus 5의 Broadcom firmware를 패치하여 항상 1 byte encryption key를 요청하도록 합니다. 타겟 디바이스가 이 약한 key를 수락하고 encryption이 성공하면, 해당 타겟은 취약한 것입니다.

이는 ESP32를 사용하여 외부 공격자로서 LMP 패킷을 가로채고 수정하는 BrakTooth KNOB과는 다릅니다. 두 방식 모두 같은 취약점을 테스트하지만, 관점이 다릅니다.

### 중요: False Positive 방지

초기 Python 스크립트는 `Read Encryption Key Size`가 1을 반환하는지만 확인하였습니다. 이로 인해 iPhone 13 Pro에서 **false positive**가 발생하였습니다. HCI 로그 분석 결과 다음과 같은 사항이 확인되었습니다:

- **Encryption Change event**의 `Status: Unsupported LMP Parameter Value (0x20)`, `Encryption: Disabled (0x00)` — iPhone이 약한 key를 **거부**하였습니다.
- 거부되었음에도 불구하고, `Read Encryption Key Size`는 여전히 1을 반환하였습니다 — 이는 register에 남아 있는 요청 값일 뿐, 합의된 key가 아닙니다.

수정된 스크립트는 이제 **두 가지 조건을 모두** 확인합니다:
1. `Read Encryption Key Size`가 1을 반환
2. `Encryption Change` event의 `Status: Success (0x00)` 및 `Encryption: Enabled`

두 조건이 모두 충족될 때만 타겟을 취약하다고 보고합니다.

### 방법론

신뢰성 있는 2단계 접근 방식은 다음과 같습니다:

1. **Phase 1 — 정상 페어링** (KNOB 패치 비활성 상태): 양쪽 디바이스에서 Numeric Comparison을 통한 SSP 페어링을 완료합니다. 이를 통해 link key가 저장됩니다.
2. **Phase 2 — KNOB 패치 설치 후 재연결**: KNOB firmware 패치가 key entropy negotiation을 수정합니다. 재연결을 트리거하면 저장된 link key를 재사용하여, 바로 authentication → encryption으로 진행됩니다. 이 방식은 0.1초 polling으로 key size를 캡처하기에 충분히 빠릅니다.

KNOB 패치가 활성화된 상태에서의 초기 페어링은 실패합니다. 전체 SSP 흐름(IO capability exchange → NC → 사용자 확인 → link key 생성)에 시간이 너무 오래 걸려 연결 window를 놓치기 때문입니다.

### 테스트 결과

#### Samsung Galaxy Note10+ 5G (64:7B:CE:BD:A5:2B)

- **Bluetooth**: 5.0, Broadcom chip (firmware 002.002.008)
- **HCI 증거** (`/tmp/knob_final.log`에서):
  - `Encryption Change`: `Status: Success (0x00)`, `Encryption: Enabled with E0 (0x01)`
  - `Read Encryption Key Size`: `Status: Success (0x00)`, `Key size: 1`
  - 약 2초 후 `Authentication Failure (0x05)`로 연결 해제
- **Python 스크립트**: `Raw: 010814000c0001` — Status 0x00, Key size 1
- **결과**: **취약함(VULNERABLE)** — 1 byte encryption key를 수락하고 encryption이 활성화되었습니다
- **일치 여부**: BrakTooth KNOB 테스트 결과와 일치합니다

#### iPhone 13 Pro (14:2D:4D:D8:3C:83)

- **HCI 증거** (`/tmp/knob_iphone.log`에서):
  - `Encryption Change`: `Status: Unsupported LMP Parameter Value / Unsupported LL Parameter Value (0x20)`, `Encryption: Disabled (0x00)`
  - `Read Encryption Key Size`: `Status: Success (0x00)`, `Key size: 1`
  - encryption 실패 후 Nexus 5가 즉시 연결 해제
- **초기 Python 스크립트 결과**: Key size 1 보고 — **FALSE POSITIVE**
- **수정된 결과**: **취약하지 않음(NOT VULNERABLE)** — iPhone이 LMP 수준에서 1 byte key를 거부하였으며, encryption이 활성화되지 않았습니다

### 핵심 교훈

**`Read Encryption Key Size`만으로는 절대 판단하지 마십시오.** 이 HCI 명령은 encryption이 실패한 경우에도 key size를 반환할 수 있습니다. `Encryption Change` event가 실제 근거(ground truth)이며, 결론을 내리기 전에 해당 event의 status code와 encryption mode를 반드시 확인해야 합니다. 항상 raw btmon HCI dump와 대조하여 결과를 검증하십시오.

### 수동 실행

cd /usr/share/BlueToolkit/modules/tools/custom_exploits

### btmon을 이용한 결과 검증

항상 Python 스크립트의 판정 결과를 raw HCI 로그와 대조 확인하십시오:

```bash
adb pull /storage/self/primary/btsnoop_hci.log /tmp/knob_verify.log

# Encryption 상태 확인 (ground truth)
btmon -r /tmp/knob_verify.log | grep -A8 "Encryption Change" | grep -v "Octet"

# Key size 확인
btmon -r /tmp/knob_verify.log | grep -A8 "Read Encryption Key Size" | grep -v "Octet"
```

취약함: `Encryption: Enabled with E0 (0x01)` + `Key size: 1`
취약하지 않음: `Status: Unsupported LMP Parameter Value (0x20)` + `Encryption: Disabled`

## 알려진 문제 및 해결 방법

| 문제 | 해결 방법 |
|------|----------|
| `fastboot`가 디바이스를 인식하지 못함 | USB 케이블을 분리 후 재연결합니다. USB 2.0 포트를 사용하는 것이 좋습니다 |
| Factory flash 시 `mke2fs` 실패 | format 대신 `fastboot erase userdata`를 사용합니다 |
| CF-Auto-Root wget redirect | 브라우저를 통해 ZIP 파일을 다운로드합니다 |
| BluetoothAssistant `INSTALL_FAILED_OLDER_SDK` | `app/build.gradle`과 `utilities/build.gradle` 양쪽에서 `minSdk`를 23으로 낮춥니다 |
| BluetoothAssistant 권한 거부 | location 및 storage 권한을 `pm grant`로 수동 부여합니다 |
| BluetoothAssistant 페어링 불안정 | Nexus 5 Bluetooth 설정 화면에서 수동으로 페어링합니다. KNOB 테스트 전에 사전 페어링합니다 |
| InternalBlue cmd2 import 오류 | BlueToolkit venv에 `cmd2==2.4.2`를 고정 설치합니다 |
| Exploit `.sh` shebang 누락 | 첫 줄에 `#!/bin/bash`를 추가합니다 |
| KNOB PoC가 interactive CLI에서 블로킹 | `bluekit_internalblue_knob.py`를 대신 사용합니다 |
| Key size 읽기 timeout | 백그라운드 thread에서 0.1초 간격으로 polling합니다 |
| KNOB false positive (key size 1이지만 encryption 거부됨) | 보고 전에 HCI callback을 통해 Encryption Change event status를 확인합니다 |
| KNOB 패치 활성 상태에서 최초 페어링 실패 | 패치 없이 사전 페어링한 후, 재연결 시 KNOB을 실행합니다 |
| 테스트 간 디바이스 페어링 해제 | `service call bluetooth_manager 10` 또는 `bt_config.conf` 삭제를 사용합니다 |
