# 20260212 진행현황

## 이전까지의 현황

BlueToolkit을 통해 두 개의 스피커 기기와 삼성 휴대폰 기기 한 대(Galaxy S7)을 대상으로 공격을 실행하는 데에 성공했습니다.

그러나 custom 익스플로잇 가운데 `custom_nino_check` 취약점 확인이 에러 및 `hcitool` 자체의 문제 때문에 실행되지 않았는데, 오늘은 iPhone 대상 공격을 제외하고 이 점을 해결하였습니다.
해결 과정 및 결과를 정리하고자 본 문서를 생성하였습니다.

`custom_nino_check`까지 정상적으로 실행하여 새롭게 진행한 공격은 모두 [오늘의 공격 실행 결과](#오늘의-공격-실행-결과) 소주제 아래 정리해두었으니 참고하여 주세요.

## `custom_nino_check` 문제 해결 (iPhone 제외)

### Error during extracting information from regex

우선 전날의 공격 결과를 살펴보면, 정규식 추출 관련 에러 때문에 `custom_nino_check` 취약점 확인이 불가했던 경우가 있었습니다. 

BlueToolkit은 `constant.py`에 정의되어있는 정규식에 따라 출력되지 않으면 파싱이 잘못되어 오류를 생성합니다:

```python
REGEX_EXPLOIT_OUTPUT_DATA = b"BLUEEXPLOITER DATA:.*\n"
REGEX_EXPLOIT_OUTPUT_DATA_CODE = b" code=[0-4],"
REGEX_EXPLOIT_OUTPUT_DATA_DATA = b", data=.*"
```

The engine captures your script's stdout, then searches for a line like:
```
BLUEEXPLOITER DATA: code=2, data=Vulnerable to NiNo attack
```

이러한 형식을 지키기 위해 bluekit은 `report_vulnerable()`, `report_not_vulnerable()`와 `report_error`라는 지정된 출력 함수를 사용합니다. 

이를 염두에 두고 BlueToolkit 내부 `/usr/share/BlueToolkit/modules/tools/custom_exploits/bluekit_nino_check.py`을 살펴보면 앞서 설명드린 `report_...` 함수를 사용하지 않아 출력이 정규식에 맞지 않는 경우를 발견할 수 있습니다. 따라서 이러한 branch 모두에 적어도 하나의 `report` 함수를 사용해주어 정규식에 맞는 출력이 나오도록 만들었습니다.

### hcitool scan과 hcitool info의 불안정성

hcitool이 같은 커맨드를 실행해도 다른 출력값을 생성하거나, 원하는 출력이 나올 때까지 여러 번 실행해야하는 경우가 있다는 점은 어제의 현황 리포트에도 언급했던 부분입니다. `bluekit_nino_check.py`에서는 `hcitool scan`과 `hcitool info`의 결과를 얻어야만 진행 흐름이 끊기지 않는데, 이때 이 두 커맨드를 모두 한 번만 실행하기에 원하는 출력을 얻지 못해서 취약점 분석이 종료되는 경우가 있었습니다. 

따라서 `hcitool scan`은 실행값이 프로그램 진행에 영향을 미치지 않도록 변경하고, `hcitool info`는 원하는 결과값이 나올 때까지 실행하는 방식으로 바꾸어주어 이 문제를 해결했습니다:

```python
def check_nino(target):
...
 # Running a scan to find the target device

                    subprocess.check_output(HCITOOL_INFO.format(target=target), shell=True)
                    print("Successfully running hcitool info")
                    break
                except subprocess.CalledProcessError as e:
```

### bluetoothctl pair의 실패

이렇게 hcitool 관련 커맨드를 모두 입력한 이후 `bluetooth pair`를 실행하는데, 이 페어링을 한 번밖에 실행하지 않아 이것이 실패할 경우 취약점 분석이 종료됩니다. 따라서 최대 10번 동안 블루투스 페어링을 시도하도록 변경했습니다:

### bluekit_nino_check.py 수정사항 요약

- 모든 경우에서 BlueToolkit의 정규식을 따르는 형태의 출력을 하도록 코드를 변경.
- `hcitool info`와 `hcitool scan`의 실행이 불안정하여 `hcitool scan`의 결과값은 무시하고 `hcitool info`의 결과값은 원하는 결과가 나올 때까지 실행하도록 변경.
- `bluetoothctl pair` 커맨드를 최대 10번 시도하도록 변경하여 페어링 보장.

## 오늘의 공격 실행 결과

오늘 진행한 취약점 분석은 ESP32와 Nexus 5를 필요로 하지 않는 모든 취약점이 대상이었습니다. 기기마다 블루투스 버전이 상이하여 실제로 실행된 취약점 분석 개수는 차이가 있습니다. 

공격 실행 시 참고하실만한 사항으로는 먼저 공격 실행 전 `sudo systemctl restart bluetooth`를 실행한 뒤 bluekit을 실행하면 에러나 연결 문제를 어느 정도 해결할 수 있다는 점이 있습니다. 또 공격을 차례대로 진행하는 동안 사이사이에 연결이 끊길 수가 있는데, 이때 해당 기기의 `hciinfo.log`가 "Requesting information ..."이라고만 나와있는지 확인하실 수 있습니다. 만약 아무런 정보가 없다면 다른 터미널에서 `sudo hcitool info [target]`을 실행해 정보를 얻고 수동으로 복사해 붙여넣으시면 됩니다. 

모든 기기에 대한 공격 결과에 에러가 발생한 취약점 수가 3개가 있는데, 이는 bluing 의존성 문제를 가진 취약점입니다. iPhone 대상 공격으로는 이에 더해 `custom_nino_check` 취약점 실행이 실패했는데, 이에 대해선 추후에 더 살펴보겠습니다. 또한 Galaxy S7 기기 두 개에 대한 공격을 보시면 한 기기에서만 취약점이 2개가 발견되는데, 같은 기종과 같은 블루투스 규격인데도 이러한 차이가 왜 나는지는 반복적인 공격 실행을 통해 밝혀내야 할 것 같습니다. 공격 결과는 하단의 표와 로그를 참고하여 주세요:
